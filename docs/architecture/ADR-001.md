# ADR-001 — API-First Architecture with Tiered Data Boundary

- **Status:** Accepted direction by existing owner decisions D-044–D-047; detailed contract and runtime not approved.
- **Date:** 2026-10-16
- **Requirements:** REQ-EXP-001, REQ-CAT-001, REQ-MAT-001, REQ-PRV-001, NFR-REL-001.
- **Related:** D-044, D-045, D-046, D-047; Q-018, Q-020.

## Context
The approved project direction selects API-first, but the privacy boundary prohibits anonymous learner-specific payloads. The current D-047 demo is local, synthetic-only, and does not require a hosted API or cloud provisioning.

## Decision
- Treat `/api/v1` as the intended API namespace and freeze the API contract before dependent API consumers are implemented.
- The initial public API tier serves curated catalogue data only.
- Anonymous matching runs in the browser. Inputs, results and tracker entries remain page-memory-only and are never sent in API requests, URLs, logs, analytics or telemetry.
- Authenticated server-side matching and saved-item/dashboard features are future gated scope under D-046; no implementation before Q-018/Q-020 and the associated identity, consent, privacy, authorization, testing and cost gates.
- The D-047 local synthetic demo remains the current implementation slice; this ADR does not authorize cloud services.

## Alternatives considered
1. Static-only catalogue with no API: lower cost/complexity, but conflicts with D-044's approved API-first direction.
2. Send anonymous marks to API for server-side matching: rejected because it violates the current privacy boundary.
3. Build all Azure services immediately: rejected because service necessity, cost, permissions and runtime behavior are not verified.

## Trade-offs and consequences
- Public catalogue data is separated from learner state, reducing accidental data exposure.
- Client matching is easier to demo locally but requires consistent deterministic rules and golden tests.
- API-first introduces contract and runtime work; API Management may be unnecessary under the budget and remains an open decision.
- The frontend must handle catalogue unavailability and malformed/stale data without invented fallbacks.

## Evidence / follow-up
API contract, CORS/cache/error/timeout details, provider logging inspection and implementation evidence are outstanding. No application build or runtime behavior is claimed.
