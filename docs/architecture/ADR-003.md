# ADR-003 — Privacy-First Anonymous Boundary and Gated Authenticated Extension

- **Status:** Current privacy boundary accepted by D-047; future authenticated controls are proposed.
- **Date:** 2026-10-16
- **Requirements:** REQ-PRV-001, NFR-PRV-001, NFR-SEC-001; future REQ-AUTH-001.
- **Related:** D-021, D-045, D-046, D-047, Q-005, Q-018, Q-020.

## Context
The primary audience includes minors. Anonymous exploration is required and privacy constraints prohibit using real learner data in the current demo. D-046 approves a future authenticated feature list, but not its implementation or data lifecycle.

## Decision
Current demo: synthetic fixtures only; no authentication, real learner inputs, durable profile persistence, uploads, analytics, profile telemetry, API transmission of learner-specific values, or tracker sync. Learner inputs/results/tracker entries remain page memory only. Academic profile persistence in a future authenticated tier requires explicit opt-in; login alone is not consent. No national IDs, household income, bank details or sensitive financial/family documents for funding matching.

Before future authenticated implementation, approve identity provider/flow, token validation, object-level authorization, ownership/isolation tests, data minimisation, consent/notice, retention/deletion, audit/logging policy, privacy/legal review and cost.

## Alternatives considered
1. Require accounts before exploration: rejected for the anonymous-first journey.
2. Store profile in localStorage/sessionStorage for convenience: rejected by current page-memory-only boundary.
3. Add authentication without lifecycle/authorization contracts: rejected as unsafe.
4. Send profile values to AI or telemetry: rejected unless a separately approved purpose and data-handling contract exists.

## Trade-offs and consequences
- Reload/exit can discard the tracker and profile inputs; communicate this clearly.
- Demo testing can use synthetic cases without collecting sensitive learner data.
- Future saved-pathway/dashboard work requires a separate security and privacy gate, not just login integration.
- Runtime privacy must be verified through browser inspection and provider-log review; design text alone is not proof.

## Evidence
No runtime privacy test, identity provider configuration or public-use legal review is claimed complete.
